# BankShield: как устроена защита

BankShield — это **упаковщик (packer) для Windows EXE**: исходная программа шифруется, к ней дописывается загрузчик **stub**, и при запуске пользователь стартует уже обёрнутый файл. Защита строится **слоями** — от криптографии до anti-debug.

---

## Общая схема

```mermaid
flowchart TB
    subgraph build [Сборка — bs_protect.exe]
        A[Исходный app.exe] --> B[Хеши + цепочка]
        B --> C[AES-256-CBC шифрование]
        C --> D[HMAC нагрузки v4]
        D --> E[HMAC заголовка + PBKDF2 wrap]
        E --> F[Склейка: stub + ciphertext + header + tail]
    end

    subgraph run [Запуск — защищённый EXE]
        G[stub.exe стартует] --> H[Проверки stub / anti-debug]
        H --> I[Разбор tail → header → ciphertext]
        I --> J[PBKDF2 unwrap ключей]
        J --> K[HMAC заголовка + ciphertext]
        K --> L[AES decrypt]
        L --> M[Хеши + цепочка]
        M --> N[Запуск через temp-файл]
    end

    F --> G
```

**Два главных компонента:**

| Компонент | Файл | Роль |
|-----------|------|------|
| **Протектор** | `bs_protect.exe` (`bs_protect_v2.c`) | Берёт `stub.exe` + ваш `app.exe` → пишет `app_protected.exe` |
| **Stub (загрузчик)** | `bs_stub.exe` | Встроен в начало защищённого файла; при запуске расшифровывает и запускает оригинал |

Есть ещё **старая версия** протектора (`bs_protect.c`) — шифрует отдельные секции PE и дописывает overlay, без stub. Основной путь сейчас — **v2 + stub**.

## Физический layout защищённого файла

С конца файла к началу (так stub ищет данные):

```
┌────────────────────────────────────────┐
│  bs_stub.exe (код загрузчика)          │  offset 0
├────────────────────────────────────────┤
│  Зашифрованный оригинальный EXE        │  payload_offset
├────────────────────────────────────────┤
│  bs_pack_header (метаданные, ключи*)    │
├────────────────────────────────────────┤
│  bs_pack_tail (магия BSHENDBB)         │  самый конец
└────────────────────────────────────────┘

* aes_key и aes_iv в файле хранятся в XOR-обёртке после PBKDF2
```

Stub открывает **свой же файл**, прыгает в конец по метке `BSHENDBB`, читает заголовок, затем ciphertext с позиции `payload_offset`.

---

## Слой 1: AES-256-CBC (конфиденциальность)

**Модуль:** `bs_crypto.c`  
**Назначение:** без ключа нельзя прочитать оригинальный EXE в файле.

**При упаковке:**
1. Генерируются случайные **ключ (32 байта)** и **IV (16 байт)** через `CryptGenRandom` / `/dev/urandom`.
2. Оригинал дополняется **PKCS#7** до кратности 16 байт.
3. Шифрование **AES-256-CBC** на месте.

**При запуске:** stub расшифровывает тем же ключом и IV (после снятия обёртки, см. слой 4).

**Что даёт:** статический анализ файла не показывает код приложения открытым текстом.

**Ограничение:** CBC без отдельной аутентификации уязвим к некоторым атакам на padding; поэтому в v4 добавлен HMAC (слой 3).

---

## Слой 2: SHA-256 хеши (простая целостность)

**Два хеша в заголовке:**

| Поле | Что хешируется | Когда проверяется |
|------|----------------|-------------------|
| `original_hash` | Расшифрованный EXE (первые `original_size` байт) | После decrypt |
| `encrypted_hash` | Зашифрованные байты на диске | До decrypt |

**Логика:**
- `encrypted_hash` — заметили правку ciphertext без знания ключа (битый файл, случайная порча).
- `original_hash` — после расшифровки убедились, что получился тот же оригинал (ошибка ключа, битый decrypt).

Это не подпись с секретом: злоумышленник с ключом может пересчитать хеши. Цель — **случайные и наивные** изменения файла.

---

## Слой 3: HMAC нагрузки v4 (encrypt-then-MAC)

**Модуль:** `bs_pack_crypto.c`  
**Только для `version >= 4`.**

**При упаковке:**
1. Из AES-ключа выводится отдельный MAC-ключ:  
   `HMAC-SHA256(aes_key, "BankShield-Payload-MAC-Key-v4")`
2. Считается  
   `payload_hmac = HMAC(mac_key, SHA256(iv || ciphertext))`
3. `payload_hmac` записывается в заголовок.

**При запуске:** тот же MAC считается **до** `AES_decrypt`. Не совпал — запуск останавливается.

**Что даёт:** защита от **подмены шифротекста** (в т.ч. padding oracle на этапе расшифровки). Это схема **encrypt-then-MAC**: сначала шифруем, потом подписываем ciphertext.

**v3:** этого слоя нет, только `encrypted_hash`.

---

## Слой 4: HMAC заголовка (целостность метаданных)

**При упаковке (до XOR-обёртки ключей):**
1. Ключ для HMAC заголовка:  
   `HMAC-SHA256(aes_key, "BankShield-HMAC-Key-Derivation")`
2. HMAC по всем полям `bs_pack_header`, **кроме** `header_hmac`.

**При запуске:** после unwrap ключей stub пересчитывает HMAC и сравнивает с `header_hmac` (сравнение за постоянное время через `bs_secure_compare`).

**Что даёт:** нельзя тихо поменять размеры, хеши, опции, соль KDF и т.д. без знания AES-ключа.

---

## Слой 5: PBKDF2 + привязка ключей к stub

**Проблема:** если положить AES-ключ в заголовок открытым текстом, любой, кто откроет файл, сможет расшифровать нагрузку.

**Решение:**
1. Считается **SHA-256 всего stub** (тела загрузчика до начала ciphertext) → `stub_hash`.
2. **PBKDF2-HMAC-SHA256**:
   - пароль = `stub_hash`
   - соль = случайные 32 байта (`kdf_salt`)
   - итерации: **10 000 (v3)** или **100 000 (v4)**
3. Получается 48 байт `hek`; ими по XOR «запутываются» `aes_key` и `aes_iv` в заголовке.

**При запуске:** stub снова хеширует свою часть файла (0 … `payload_offset`), гоняет PBKDF2 с той же солью и итерациями, XOR снова снимает обёртку.

**Что даёт:**
- Ключи **привязаны к конкретному stub**. Подменили stub — расшифровка не сойдётся.
- PBKDF2 замедляет перебор, если кто-то пытается угадать обёртку без знания stub.

**Важно:** это не HSM; при полном доступе к файлу и stub анализ всё равно возможен.

---

## Слой 6: Полиморфная цепочка хешей

**Модуль:** `bs_hash_chain_generate` / `bs_hash_chain_verify` в `bs_crypto.c`  
**Включается флагом** `BS_OPT_INTEGRITY_CHECK` (по умолчанию включён).

**Идея:** один SHA-256 от файла легко подделать, если известен алгоритм. Цепочка добавляет **соль + 8 уровней + 200 итераций HMAC на уровень**.

**Построение (упрощённо):**
```
Уровень 0: SHA256(соль || оригинальный_EXE)
Уровень 1..7: HMAC-растягивание предыдущего уровня (200 раз)
              + смешивание с уровнем 0 + номер уровня
Финал: HMAC от всей цепочки → chain_final
```

В заголовок пишутся: `chain_salt`, `chain_iterations`, 8× `chain_hashes[]`, `chain_final`.

**При запуске:** после расшифровки stub пересчитывает цепочку по расшифрованным байтам и сверяет с заголовком.

**«Полиморфность»:** при каждой упаковке **новая случайная соль** → другие значения цепочки при том же EXE. Это усложняет заранее заготовленные коллизии, но не магия.

**Что даёт:** проверка, что расшифрованное содержимое — **тот же** оригинал, который упаковывали (не подменили только ciphertext умно).

---

## Слой 7: Самопроверка stub

**Поле:** `stub_text_hash` — SHA-256 секции **`.text`** stub на этапе упаковки.

**При запуске:** stub хеширует свою `.text` в памяти и сравнивает с `stub_text_hash`.

**Что даёт:** если кто-то **пропатчил** загрузчик (NOP, jmp, вставка отладочных инструкций), запуск прервётся.

Связано с `stub_hash` для KDF, но цели разные: KDF — ключи, `.text` — неизменность кода загрузчика.

---

## Слой 8: Anti-debug (опционально)

**Модуль:** `bs_antidebug.c`  
**Флаг:** `BS_OPT_ANTI_DEBUG` (включён в `BS_OPT_DEFAULT`).

**Проверки в stub** (`stub_check_debugger`):
- `IsDebuggerPresent`
- флаг `PEB.BeingDebugged`
- `NtGlobalFlag` (типичные флаги кучи при отладке)
- `NtQueryInformationProcess` (DebugPort, DebugObject, DebugFlags)
- удалённый отладчик
- **RDTSC** — задержка на простом цикле
- поиск **0xCC** (INT3) в своём коде
- аппаратные breakpoints (DR0–DR3)

Проверка **до** расшифровки и **ещё раз** перед запуском payload.

**В библиотеке** также есть: VM (CPUID, DLL VMware/VBox), API hooks — используются в тестах / `bs_antidebug_scan`, в stub упрощённый набор.

**Реакция:** `stub_fatal` / `ExitProcess` — процесс завершается.

**Для банка:** часто спорно (мешает поддержке, легитимным отладчикам). Отключается: `--no-antidebug`.

## Слой 9: Скрытие и запуск

**Не криптография, но часть «защиты среды»:**

| Опция | Поведение |
|-------|-----------|
| `BS_OPT_HIDE_TEMP` | Временный расшифрованный EXE с атрибутами hidden/system |
| Запуск | Расшифрованный EXE пишется во **temp**, затем `CreateProcess` (RunPE отключён из‑за ошибок загрузчика) |
| Затирание | После записи буфер в памяти затирается (`stub_secure_wipe`) |
| Консоль | Stub собран как GUI; для консольных программ вызывается `AllocConsole` |

**Слабое место:** на диске на короткое время лежит **открытый EXE**. Флаг `BS_OPT_MEMORY_ONLY` в заголовке зарезервирован, но не реализован.

---

## Слой 10: Динамический резолв API (скрытность stub)

**В `bs_stub.c`:** чувствительные API (`NtUnmapViewOfSection`, `WriteProcessMemory`, …) не импортируются по имени в IAT, а ищутся через **хеш djb2** + `GetProcAddress`.

**Цель:** меньше «палевных» строк и импортов в таблице — для анализа stub чуть сложнее.

Используется в коде **RunPE** (process hollowing); основной путь запуска сейчас — temp-файл.

## Дополнительные модули (не в основном pipeline v2)

### Шифрование строк (`bs_string_crypt.c`)
XOR-обфускация строк в рантайме, чтобы тексты ошибок не светились в бинарнике stub открытым текстом.

### Безопасная память (`bs_secure_mem.c`)
Шифрование буферов в куче, канарейки, guard-страницы, затирание при `free` — для демо и тестов, не ядро упаковщика.

### PE Protector v1 (`bs_protect.c`)
Шифрует **отдельные секции** PE (код/данные) внутри одного файла, master-хеш, overlay с `protection_pack`. Без отдельного stub — другая архитектура.

### Целостность PE (`bs_integrity.c`)
Манифест секций PE (SHA-256 + CRC32) — задел для встраивания в сам PE; в stub v2 не в основном пути.

## Порядок проверок при запуске (stub)

Упрощённая последовательность:

1. Резолв API по хешам  
2. Путь к себе → открыть файл  
3. Tail magic `BSHENDBB`  
4. Прочитать `bs_pack_header`  
5. Самопроверка `.text` stub  
6. PBKDF2 → снять XOR с `aes_key` / `aes_iv`  
7. HMAC заголовка  
8. Anti-debug (если включён)  
9. Прочитать ciphertext  
10. `encrypted_hash`  
11. **v4:** `payload_hmac`  
12. AES decrypt  
13. `original_hash`  
14. Полиморфная цепочка (если включена)  
15. Anti-debug снова  
16. Temp-файл → `CreateProcess` → ожидание выхода

```
bs_protect input.exe output.exe [--no-antidebug] [--no-integrity] [--no-hide] [--stub path]
```

| Флаг | Отключает |
|------|-----------|
| `--no-antidebug` | Слой 8 |
| `--no-integrity` | Слой 6 (цепочка) |
| `--no-hide` | Скрытые атрибуты temp-файла |

## Честные ограничения (важно для собеседования)

1. **Ключи всё равно восстанавливаются в памяти** при запуске — с правами на процесс и отладку защита обходится.  
2. **Временный файл** — слабое звено.  
3. **Свой AES** вместо аудированной библиотеки — для продакшена в банке обычно CNG/libsodium.  
4. **Anti-debug** — не security boundary, а замедление анализа.  
5. Это **обфускация/упаковка**, а не DRM уровня HSM или облачной лицензии.

## Краткая таблица «слой → от чего защищает»

| Слой | От чего защищает |
|------|------------------|
| AES-256-CBC | Чтение кода без ключа |
| SHA-256 хеши | Случайная порча файла |
| Payload HMAC (v4) | Целенаправленная подмена ciphertext |
| HMAC заголовка | Подмена метаданных упаковки |
| PBKDF2 + stub binding | Отвязка ключей от чужого stub / замедление перебора |
| Цепочка хешей | Подмена содержимого оригинала |
| stub .text hash | Патч загрузчика |
| Anti-debug | Отладка в процессе защиты |
| Скрытие temp | Тривиальный поиск расшифрованного файла |

Если нужно, могу отдельно разобрать **только криптографию** (с формулами PBKDF2/HMAC) или **только путь кода stub** по функциям в `bs_stub.c` — напиши, что интереснее для подготовки к собеседованию.
